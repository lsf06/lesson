## 1. 测试范围与参与者

* **测试方法**：同伴测试（Peer Testing），由同班同学（成年）按统一脚本操作页面，我们在旁观察并记录原话，不打断、不代操作（仅在用户主动提问且卡住时给予一次口头提示）。
* **样本数**：**2 人**（同伴 A、同伴 B），使用同一台设备（ESP32-S3-EYE @ COM4）、同一 Flask 服务（10.1.41.43:5000）、同一浏览器，依次单独进行。
* **范围与局限**：
  * **样本仅 2 人，不具备统计意义**，百分比只能描述这 2 人的表现，不能作为系统整体可用性结论。
  * 两人均为具备一定数字素养的成年在校学生，结论**不外推**至儿童、老年人或非技术用户。
  * 记录方式为现场纸笔笔记 + 事后复述用户原话，**无录像、无量表、无点击埋点**，“约 2 秒”为主观估计值。
  * 本轮只覆盖“点击采集”与“断网提示 / 降级横幅”两类场景；**过期/重复指令场景同伴未执行**，仅有开发者自测，见 3.3。
* **隐私声明**：测试过程仅采集加速度数据、网络状态和模拟图像，**未采集任何真实行踪、人脸和健康判断**，未录制人脸与声音。

## 2. 核心观测项与真实统计（n=2）

| 观测项 | 第9周（中期版本，定性观察） | 第16周（本轮真实记录，n=2） | 结果 |

| **误触（重复点击）** | 未统计 | A 等待约 2 秒后询问“是不是没点上？”并再次点击 | 误触 **1/2 = 50%** |

## 3. 原始观察记录

### 3.1 同伴 A（第一轮）

**场景 1：点击“采集一次最新数据”**

* A 点击后盯着顶部状态区，**约 2 秒**没看到明显进展（按钮其实已置灰、文案已变成“⏳ 提交中…”，但 A 没注意到这块变化）。
* A 原话：**“是不是没点上？”**，手已经移到按钮上**再次点击**，产生 1 次重复请求。
* 我们没有立即阻止，用于观察真实行为；服务端按 `request_id` 幂等处理，未产生重复入库。

**场景 2：断网（关闭 Wi-Fi），等待 10 秒后恢复**

* 断开后页面进入离线态：状态点熄灭、显示 `● OFFLINE`，多源状态卡片灰化。
* A 原话：**“知道数据没丢，但不知道什么时候能传上去。”**
* 恢复网络后数据回填，A 没有追问是否丢数据，但也**没有主动确认补传是否完成**——因为界面没告诉他“已补传几条”。
* 串口侧可同时看到 `Cached locally (queue=n/20)` 与 `RETRANSMIT: sending N cached records`（开发者在旁记录，A 未看串口）。

### 3.2 同伴 B（第二轮）

**场景：打开页面即看到顶部黄色横幅**

* B 第一眼看到黄条后问：**“这是系统坏了吗？”**
* 我们按脚本给了一次中性解释：“这是外网不可用、系统改用本地规则”，B 表示理解，后续操作正常。
* 补充观察：B 没有把黄条与“功能仍可用”联系起来——先判断为“故障告警”，解释后才转成“降级”。也就是说，**文案本身没完成传达**。
* B 未参与断网恢复场景（本轮只安排 A 做该场景）。

### 3.3 未由同伴验证的部分（如实标注）

* **过期指令 / 重复指令**：2 名同伴均未执行该场景，因此**没有用户侧观察数据**。
* 仅有开发者自测：注入 1 条 30 秒前已过期的指令后，ESP32 串口打印
  `Task expired, skipped: request_id=... now=... expire_at=...`，服务端记录 `EXPIRED` 回执且未产生重复写入。
* 这属于**功能验证**，不是用户体验结论，不计入上表的用户指标。

### 3.4 失败尝试记录（保留）

1. **A 的重复点击**：点击后约 2 秒无反馈 → 判定“没点上” → 连点 2 次（1/2 用户误触）。
2. **B 的横幅误读**：把黄色降级横幅理解成“系统坏了”（1/2 用户误读）。
3. **A 的补传时机困惑**：知道数据没丢，但不知道何时补传、传了几条（1/1 用户在此项未获得答案）。
4. **记录方法的缺陷**：第一次测试忘记记录 A 从点击到按钮变色的具体时长，只留下“约 2 秒”的主观估计；下一轮应使用秒表或录屏。

## 4. 问题 — 证据 — 修改建议

| 发现问题 | 证据（用户原话 / 行为 / 日志） | 修改建议与状态 |
| :--- | :--- | :--- |
| **点击后无可见进度，2 秒就被判为“没点上”并连点** | A：“是不是没点上？”并再次点击（误触 1/2）；前端点击后仅置灰 + 文案变“⏳ 提交中…”，无倒计时/进度条 | **建议（未实施，下一版优先）**：点击后在按钮或状态区显示 **loading 倒计时**（如“已提交，预计 ≤5s…3s”），倒计时结束前禁用重复提交。目前只有服务端 `request_id` 幂等兜底——属于“错了也不会坏”，但用户仍会焦虑 |
| **黄色横幅被读成“系统故障”** | B：“这是系统坏了吗？”（1/2 误读）；现文案“⚠️ 外网不可用：本地基础反馈仍可用” | **建议（未实施）**：文案改为更友好的 **“系统已切换至本地离线模式，功能正常可用”**，去掉“不可用 / ⚠️”的故障语义，改成中性状态说明 |
| **断网只说明状态，不说明补传进度** | A：“知道数据没丢，但不知道什么时候能传上去”；恢复后界面无“补传 N 条”的显式提示 | **建议（未实施）**：灰条补充队列信息（“已本地缓存 N 条，恢复后自动补传”），恢复后给出“已补传 N 条”的结果提示 |
| **记录方法不规范** | 等待时长为主观估计“约 2 秒”，无录屏、无秒表、无固定脚本 | **建议（流程改进）**：下一轮用秒表计时 + 屏幕录制，提前准备 3 条固定任务脚本，避免临场补记 |

> 以上 3 条产品侧建议**均未落地**，本轮只做评估、未改动被测版本代码，请勿把建议当作已修复项。

## 5. 总结

本轮只有 **2 名成年同伴**参与，结果比模板版难看，但这才是真实情况：**首次无人提示即顺利完成采集的只有 1 人（50%）**，误触 1 人（50%），把黄色降级横幅误读为故障 1 人（50%），断网后“知道数据没丢但不知道何时补传”1 人（占断网观察者 100%，样本仅 1 人）。

第13-15周的容错机制在**功能层面是成立的**（缓存不丢数据、幂等防重复入库、过期指令被拦截，均有串口与服务端日志支撑），但**“机制做对了”不等于“用户看懂了”**：本轮暴露的 3 个问题全部集中在反馈文案与进度可视化上，而不是容错逻辑本身。

下一步优先级：① 采集按钮的 loading 倒计时；② 黄色横幅改为“系统已切换至本地离线模式”；③ 断网/恢复时显示补传条数与结果。由于样本仅 2 人，以上只能作为改进线索，需用更大样本（≥8 人）复测后才谈得上“可用性达标”。
